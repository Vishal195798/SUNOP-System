SUNOP - SOLAR UNIFIED NETWORK OPERATION PLATFORM
PROJECT DETAIL REPORT

1. PROJECT OVERVIEW
Name: SUNOP
Full Name: Solar Unified Network Operation Platform
Purpose: Monitor, manage, and report on solar plant operations through a centralized web dashboard.
Application Type: Full-stack web application
Architecture: Browser-based frontend and Spring Boot REST backend connected to a MySQL database
Primary Backend URL: http://localhost:8080
Frontend Entry Pages:
- login.html - Admin login page
- step.html - Main operational dashboard

4. MAIN JAVA CLASSES
SolarBackendApplication.java:
- Starts the Spring Boot application
- Main entry point for the backend server

LoginController.java:
- Provides the admin login API
- Compares submitted credentials with demo admin credentials
- Returns success, username, role, and message in JSON

SolarController.java:
- Retrieves and inserts solar readings
- Calculates today, weekly, monthly, and plant-wise energy reports
- Generates current alerts and alert history
- Supplies settings information from the latest solar reading

SolarPlantController.java:
- Retrieves all configured solar plants

SolarData.java:
- JPA entity mapped to the solar_data table
- Stores readings, plant metadata, and timestamps

SolarPlant.java:
- JPA entity mapped to the solar_plants table
- Stores plant name, location, capacity, panel count, and status

SolarDataRepository.java:
- Extends JpaRepository
- Retrieves the latest record
- Executes native MySQL queries for daily, weekly, monthly, and plant-wise totals

SolarPlantRepository.java:
- Extends JpaRepository
- Provides CRUD access to solar plant records

6. SOLAR_DATA ENTITY
Table: solar_data
Fields:
- id: Auto-generated primary key
- voltage: Double voltage reading
- current: Double current reading
- power: Double power reading
- temperature: Double panel temperature
- energy_today: Daily energy value
- status: Operational status text
- plant_name: Name of the associated plant
- location: Physical location of the plant
- capacity: Plant capacity
- total_panels: Number of panels
- plant_id: Optional integer identifier linking readings to a plant
- created_at: Reading creation timestamp

7. SOLAR_PLANTS ENTITY
Table: solar_plants
Fields:
- id: Auto-generated primary key
- plant_name: Plant name
- location: Plant location
- capacity: Plant capacity
- total_panels: Number of solar panels
- status: Plant status

Session values stored in browser Local Storage:

- sunopUsername = admin or logged-in username
- sunopRole = ADMIN

Direct Admin Access:
The Admin Access button on login.html bypasses credential entry for this demo application. It stores the admin session values and immediately opens step.html.

Important security limitation:
The application currently uses demo credentials and client-side session checks. It does not use server-side sessions, JWT authentication, password hashing, or protected backend routes. This login should not be treated as production security.

10. REST API ENDPOINTS
Authentication:
- POST /login - Validates demo admin credentials

Solar readings:
- GET /solar - Returns all solar records
- GET /solar/latest - Returns the newest solar record
- POST /solar - Inserts a solar record

Reports:
- GET /reports - Returns today, weekly, and monthly energy totals
- GET /reports/daily - Returns daily aggregate energy history
- GET /reports/plant/{plantId} - Returns daily history for a selected plant

Alerts:
- GET /alerts - Returns alerts generated from the latest reading
- GET /alerts/history - Returns historical non-normal alerts

Plants:
- GET /plants - Returns all configured solar plants

Settings:
- GET /settings - Returns the latest plant and system settings values

All controllers use @CrossOrigin, allowing browser cross-origin access during local development.

11. BACKEND REPORT LOGIC
Today energy:
- Uses the maximum energy_today for each plant on the current date
- Sums the plant totals

Weekly energy:
- Uses records from the current date through the previous six days
- Produces a rolling seven-day result

Monthly energy:
- Uses records from the current date through the previous 29 days
- Produces a rolling 30-day result

Daily energy history:
- Groups readings by date and plant
- Uses the maximum energy_today for each plant per date
- Sums plant totals per date

Plant-wise history:
- Filters by plant_id
- Groups readings by date
- Uses the maximum energy_today for that plant per date

17. PROJECT WORKFLOW SUMMARY
1. The user opens login.html.
2. The user enters admin credentials or clicks Admin Access.
3. The login JavaScript stores the SUNOP session values in Local Storage.
4. The browser redirects to step.html.
5. step.html verifies sunopLoggedIn and redirects to login.html if absent.
6. The frontend calls Spring Boot REST APIs.
7. Spring Boot reads or writes MySQL records through JPA repositories.
8. The dashboard displays current readings, plant data, reports, alerts, and settings.
9. Logout removes Local Storage session values and returns to login.html.
